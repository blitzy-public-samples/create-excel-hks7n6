# Security Decision Log

The single source of truth for **why** each security control in this repository is shaped the
way it is. Code carries only terse statements of the threat closed and the contract enforced;
every alternative considered, every trade-off accepted and every deviation from a literal
reading of the requirements is recorded here.

Cite an entry by its ID (`D3`, `DEV-2`, `R7`). Source files carry no citation of these
entries — see R27 — so this file is found by name, and each entry names the artifacts it
governs.

## 1. Remediation decisions

| ID | Decision | Alternatives considered | Why this choice | Risks it carries |
|----|----------|-------------------------|-----------------|------------------|
| D1 | Bridge identity by verifying the Firebase ID token inside the existing `get_current_user`. | (a) Mount a `/token` route issuing the existing HS256 JWT; (b) run both paths in parallel. | Fewest files touched given the Firebase-first client flow: 4 files versus 8 or more. A `/token` route would need a new module, router registration, a password column on `User`, a credentials schema, migration tooling that does not exist, and a client rewrite away from the Firebase front door. It would also depend on the `passlib` + `bcrypt` path proven broken in D15. | Every request now performs token verification, so a Firebase outage becomes an authentication outage. Mitigated by `auth_token_verifier`, which selects the legacy path per request with no restart. |
| D2 | Resolve relational identity through the verified `email` claim rather than adding a `firebase_uid` column. | Add `firebase_uid` with a migration; key on the UID with no relational lookup; keep a separate mapping table. | `User.id` is an `Integer` primary key with no `firebase_uid` and no password column, and the repository has **no migration tooling** — `scripts/deploy.sh` still carries an unresolved "specify the migration tool" placeholder. `User.email` is unique and non-null, so it is the only mapping needing no schema change. | Runs against Firebase's own guidance that email addresses change while UIDs never do. A user changing their Firebase email loses their relational identity. Produces a deliberate asymmetry: `firestore.rules` keys on the immutable `request.auth.uid`, the relational bridge keys on email. Adding `firebase_uid` is follow-up F5. |
| D3 | Return a V4 signed URL from `upload_file` rather than proxying object bytes through an authenticated endpoint. | An authenticated backend proxy streaming object bytes; a short-lived per-object token scheme. | Signed URLs were the first-listed preference and the change is confined to two lines inside an existing method. A proxy would need a new route, response streaming and a client change. | Requires `iam.serviceAccounts.signBlob`, which cannot be limited by IAM conditions and lets its holder sign on behalf of any service account in the project — a real privilege-escalation surface. Mitigated by scoping `roles/iam.serviceAccountTokenCreator` to one dedicated signer account (see R8). The proxy remains the documented fallback if the grant is refused by policy. |
| D4 | Remove `blob.make_public()` no later than enabling uniform bucket-level access. | Enable the bucket policy first; enable it in a later change. | Once uniform bucket-level access is enabled, requests that set or modify object ACLs fail with HTTP 400, and `make_public()` **is** an object-ACL write. Applying the bucket policy first would break uploads. | The constraint reverses on rollback: reverting `file_storage.py` alone restores a call that now fails with HTTP 400. **Both must be reverted together** — this is a rollback precondition, not a preference. |
| D5 | Enforce public access prevention on `user_uploads` but only uniform bucket-level access on `static_assets`. | Enforce on both; enforce on neither; serve the SPA from a private bucket behind Cloud CDN. | `static_assets` intentionally serves the public SPA, and enforcing public access prevention there would break the site. Uniform access still removes ACL-based drift. | An intentionally asymmetric posture across two buckets invites confusion. Mitigated by documenting the asymmetry and its reason in `SECURITY.md`. Private-bucket serving via Cloud CDN would allow uniform enforcement and is follow-up F12. |
| D6 | Implement rate limiting as middleware — a global ceiling plus a write-method tier — rather than per-route decorators. | `@limiter.limit` decorators per endpoint; an API-gateway quota; Cloud Armor. | Decorators require a `request: Request` parameter on every handler, which the "no refactoring beyond the auth dependency" boundary forbids. The middleware design needs **zero** handler changes, so it is the only compliant design rather than merely the tidier one. | Coarser granularity: the high-frequency `PUT .../cells` endpoint shares the global ceiling instead of having its own tuned limit. Mitigated by keeping both thresholds configuration values and requiring validation against real autosave cadence before promotion. Counting is per process and forwarded client addresses are not consulted; see R21. |
| D7 | Use `sslmode=require` with Cloud SQL `ssl_mode = "ENCRYPTED_ONLY"`. | `sslmode=verify-full` with `TRUSTED_CLIENT_CERTIFICATE_REQUIRED`; the Cloud SQL Python Connector. | The mandate was a configuration-only change. `verify-full` needs CA material distributed to the client and connection by DNS name; the Connector needs a new dependency and new connection code. | `require` encrypts but does not authenticate the server, so it defeats passive interception but not a determined active machine-in-the-middle. Both stronger options are follow-ups F8 and F9. |
| D8 | Set only `ssl_mode` in Terraform, never the legacy `require_ssl`. | Set both; set `require_ssl` alone. | `ssl_mode` is the current attribute and supersedes `require_ssl`; setting `ssl_mode` while the provider defaults `require_ssl` to false produces a conflict. | A provider version that still requires `require_ssl` would fail the plan. Detected immediately at `terraform plan`, and the provider is now version-constrained (R7). |
| D9 | Deliver security headers at four points: API middleware, `index.html` meta tags, `nginx.conf`, and Terraform backend-bucket custom response headers. | Nginx only; meta tag only; API middleware only. | The compiled SPA ships to a Cloud Storage bucket by `gsutil rsync` while the Nginx image is never deployed, so Nginx-only headers would reach nobody. CSP's `frame-ancestors` is ignored inside a `<meta>` tag, so the meta tag cannot deliver framing protection. Each point covers a path the others do not. | Four places to keep consistent; drift is possible. Mitigated by defining the canonical set once in `backend/app/core/security_headers.py`, referencing it from each artifact, and rendering the variable part rather than duplicating it (R10, R11). |
| D10 | Register the header middleware **last**, so it is outermost. | Register it first; register it inside the CORS middleware. | Verified by execution: with the header middleware outermost, CSP is present on the 401, on the 429 **and** on the CORS preflight response. Registered inner, error and preflight responses escape uncovered. | A future middleware addition that assumes registration order could silently reduce coverage. Mitigated by tests asserting headers on 401, 429 and preflight. |
| D11 | Include `try_files $uri $uri/ /index.html` in the Nginx configuration. | Ship headers only. | The `COPY nginx.conf` line was commented out, so the container served with default Nginx and no SPA fallback. Activating a configuration without `try_files` would newly break deep links — a security fix causing a functional regression. | None material; the directive is standard for a single-page application. |
| D12 | Author Firestore rules that fail closed, accepting that they deny all client access until an out-of-scope writer populates `ownerUid`. | Allow any authenticated user (`request.auth != null` alone); defer the rules until `ownerUid` exists; modify `real_time_sync.py`. | A signed-in-is-enough rule would admit every authenticated user to every workbook document — the exact exposure V10 exists to close, so it was **rejected as insecure**. Deferring leaves a Critical gap open. `real_time_sync.py` is outside the allowed change set. Fail-closed is the only safe option available in scope. | Client-side collaboration is denied until `ownerUid` is populated. Bounded: the client path is already non-functional, and server client libraries bypass rules entirely, so backend writes are unaffected. Populating `ownerUid` is follow-up F4. |
| D13 | Add no in-handler ownership checks, leaving an authenticated cross-tenant read possible. | Add ownership guards in the three path-parameterised handlers; pass an owner filter into the service calls. | The boundary permits route edits only for adding an auth dependency and forbids any business-logic route behaviour beyond it. An ownership guard is business logic, and implementing it properly needs the excluded domain service layer. | **A real residual**: any authenticated user can still address another user's `workbook_id`. Still a strict improvement — an unauthenticated leak becomes authenticated, attributable access. Highest-priority follow-up F2. |
| D14 | Pin `python-jose[cryptography]==3.5.0`. | Leave it unpinned; replace it with `PyJWT`. | The advisory records `python-jose < 3.4.0` as affected by CVE-2024-33663 (algorithm confusion, CWE-327), fixed in 3.4.0. Without a pin a future build could resolve below that floor. Replacement would contradict the instruction that `python-jose` remains as-is. | Retains the transitive `ecdsa` PYSEC-2026-1325, which has **no published fix**. Bounded: after D1 the live authentication path uses `firebase-admin`, leaving `python-jose` only for the retained `create_access_token` helper. |
| D15 | Pin `bcrypt==4.0.1`. | Leave it unpinned; upgrade `passlib`; drop `passlib`. | Demonstrated by execution: `bcrypt` 5.0.0 makes `passlib` 1.7.4 raise `AttributeError: module 'bcrypt' has no attribute '__about__'` and then `ValueError: password cannot be longer than 72 bytes`. `security.py` builds `pwd_context` at module scope, so an unpinned resolution breaks the module on import. | Pins to an older release that may itself accrue advisories. Bounded: after D1 nothing in the live path calls `passlib`. |
| D16 | Pin `pydantic==1.10.26`. | Migrate to Pydantic v2 with `pydantic-settings`. | `backend/app/core/config.py` uses the v1 `from pydantic import BaseSettings`; v2 moved it to a separate distribution, so a v2 resolution raises `ImportError` on the first line of the configuration module. Migrating is a framework change far outside a security fix. | Holds the project a major version behind. Follow-up F11, not a security item. |
| D17 | Build rollback on configuration toggles plus a tagged `git revert`, not image rollback. | Rely on image rollback; blue-green deployment. | Images are tagged `:latest` only and overwritten on each deploy, so **no prior image exists to roll back to**. | Configuration rollback cannot undo a code defect. Mitigated by staging every change before production. |
| D18 | Provide `auth_enforcement_enabled` as a break-glass switch, defaulting to `True`, with mandatory warning logging and a response marker when disabled. | Omit it entirely; make it staging-only. | The requirement was explicit: the auth dependency must ship behind a toggle that can be disabled quickly without a full redeploy. | **Exercising it reopens V1 in full.** Mitigated by the secure default, a per-request warning log, a marker response header for auditability, documentation as break-glass-only, and the recorded preference that reverting the client interceptor is the better lockout remedy. |
| D19 | Run the dependency-audit CI gate non-blocking against a committed advisory baseline, failing only on a delta. | Block on any advisory; omit the scan entirely. | Every published fix version for the reported advisories requires Python 3.10 or newer, so a blocking gate would fail on its first run and every run after, training the team to ignore it. The baseline must also carry `GHSA-6hr6-w5qg-qmwg` for `h2`, which arrives through `firebase-admin`'s `httpx[http2]` requirement and is therefore not removable. | A genuinely serious new advisory in an already-listed package could be missed if the baseline is not curated. Mitigated by reviewing the baseline whenever the manifest changes, and by making a strict gate an exit criterion of the runtime upgrade (F1). |
| D20 | Declare `gcs_bucket_name` in lower case, matching the existing reference. | Normalise to `GCS_BUCKET_NAME` for consistency with the six original fields. | The instruction was that new fields be added, not renamed, naming the lower-case form explicitly. It also avoids touching `file_storage.py`. | Inconsistent casing within `Settings`. Cosmetic, and deliberately not "corrected" because the instruction is explicit. Pydantic matches field names case-insensitively, so either spelling resolves. |
| D21 | Do not add a `/token` route. | Add one for completeness; add one behind a flag. | With D1 a token-issuing route is avoidable, and adding one would introduce a new unauthenticated endpoint that must itself be rate-limited and hardened — new attack surface for no benefit. | If Firebase were ever removed, no fallback token issuer exists. Bounded: `create_access_token` is retained intact, so a route can be added later without touching the security module. |
| D22 | Validate Firestore rules with the emulator as a documented procedure rather than a committed JavaScript test harness. | Commit `@firebase/rules-unit-testing` tests. | A test harness would add a frontend dependency, contradicting the requirement that no frontend dependency changes be made. | Rules are not machine-verified in CI. Mitigated by exact emulator commands in the verification procedure and by rules simple enough to review by inspection. Follow-up F13. |
| D23 | Place new developer and security documents under `documentation/` rather than a new `docs/` tree. | Create `docs/security/`; put everything in `README.md`. | The repository already has a `documentation/` directory, and the onboarding rule requires filling gaps rather than duplicating structure. | Mixes specification documents with developer guides in one directory. Mitigated by explicit filenames. |
| D24 | Correct the `README.md` stack description rather than preserving it. | Leave it and add a new document; append a correction note. | The stack section is not stale — it describes a **different application** (Node/Express/MongoDB, `MONGODB_URI`, `npm run dev`) and links two files that do not exist. Nothing there is accurate enough to preserve. | Rewriting documentation risks losing intent the original author had. Mitigated by replacing only demonstrably wrong content and leaving the structure intact. |
| D25 | Require `AuthEnforcementBypassMarkerMiddleware` to be registered as the innermost middleware, and state that contract on the class. | Carry the bypass on `scope['state']` instead of a `ContextVar`, so ordering stops mattering; drop the marker header and rely on the warning log alone; leave the ordering undocumented. | The bypass is resolved in a worker thread, so it travels back to the request scope through a mapping and is republished on a `ContextVar` for the middleware to read. Starlette's `BaseHTTPMiddleware` runs everything downstream of itself in a separate task whose context copy does not propagate back, so the flag is invisible across one. Reaching `scope` instead would mean giving `get_current_user` a `Request` parameter, and its signature is a named contract that must not change. | The constraint is documentation, not enforcement: registering the middleware anywhere else still admits and still logs the request, and only the marker header is lost. Tracked as residual 13 and follow-up F20. |

| ID | Literal reading | What was done instead | Why the deviation is justified | Risks it carries |
|----|-----------------|-----------------------|--------------------------------|------------------|
| DEV-1 | The allowed change set names `frontend/public/index.html` for security headers only, and does not list `frontend/src/services/api.ts`. | `api.ts` gained a Firebase initialization path, a dedicated Axios instance, a request interceptor that attaches the Firebase ID token, and sanitized error logging. | The requirements' own risk analysis states that wiring authentication "may reveal that the client does not yet send any token at all... requiring a coordinated client-side change to attach a token to requests — this is the largest risk," and warns that users "could be locked out of all functionality until the client-side change ships **in the same rollout**." ## 3. Review-response decisions

Judgement calls made while resolving the security code review. Each names the finding it answers.

| ID | Finding | Decision | Alternatives considered | Why this choice | Risks it carries |
|----|---------|----------|-------------------------|-----------------|------------------|
| R1 | F4 | Admit the Firebase `email` claim as the local identity whenever it is a non-empty string, and require nothing else of the token's claims. **Supersedes the earlier decision to additionally require `email_verified` to be exactly `True`.** | Keep the `email_verified` gate; keep it but have the client drive `sendEmailVerification` and block sign-in until the address is confirmed; require a Firebase custom claim; map on `uid` with a schema migration. | The preserved Firebase email/password sign-in flow in `frontend/src/services/auth.ts` neither checks nor initiates address verification, so the gate admitted a user to sign-in and then answered 401 to every one of their API requests — a valid user locked out of the whole application. The Agent Action Plan specifies this bridge as the verified token's `email` claim resolved against `User.email` and specifies no verification state, so the gate was an extra admission policy beyond the minimum bridge, and closing it by adding a verification workflow would have been a new feature in a minimal remediation. The non-empty-**string** requirement is retained, so a null, empty, numeric or otherwise non-string claim still yields 401 and never reaches the query. | A Firebase account that never proved control of an address can now select the local `User` row holding that address, so an attacker who can self-register against a known user's address inherits that user's data. Recorded as residual 14; closed properly by F5 (map on the immutable `uid`) or F21 (require verification at the identity provider), and mitigable today by restricting who may create accounts in the Firebase project. |
| R2 | F4 | Resolve identity through one shared path, used by both the enforced and the `auth_enforcement_enabled = false` bypass path. | Give the bypass path its own looser resolution; give it its own stricter resolution. | One identity-resolution path is easier to reason about than two, and a second path is exactly where a future reader introduces a hole. Both paths therefore apply the same non-empty-string `email` requirement and the same `sub` truthiness requirement. | None beyond R1's residual: the bypass path reads unsigned claims, so the requirement is worthless against an attacker there. Accepted — D18 documents break-glass as never-in-production. |
| R3 | C-2 | Keep the legacy HS256 path's existing truthiness check on `sub` rather than imposing the string requirement. | Require a string `sub` on both paths for symmetry. | `sub` is compared against `User.id`, an `Integer` column, so a locally-minted token legitimately carries an integer. Requiring a string would break the retained legacy verifier — a regression in a path the rollback design depends on. | The legacy path admits any truthy `sub` type. Bounded: `firebase` is the default verifier and no route mints HS256 tokens (D21). |
| R4 | M-4 | Pass `check_revoked=True` to `verify_id_token`, and add `UserDisabledError` to the failure set that maps to 401. | Leave the default (`False`) and accept the replay window; check revocation only on mutating requests. | With the default, a signed-out, password-reset or administratively disabled user keeps API access for the remaining lifetime of an already-issued token. The check closes that window for every route at once. | Adds a user-record lookup per request, which the Admin SDK serves over the network. Accepted as the cost of revocation awareness; if latency becomes a problem the setting is the natural place to make it configurable. |
| R5 | M-4 | Map `CertificateFetchError` to the same logged 401 as the other verification failures. | Leave it unhandled so it surfaces as a 500, on the grounds that a certificate-fetch failure is an infrastructure fault rather than a bad credential. | `CertificateFetchError` is not a subclass of `InvalidIdTokenError`, so leaving it out of the exception tuple let it escape `get_current_user` as an **unhandled** 500 with no controlled response and no log line of its own. Every verification failure now takes one path: the existing 401 with a `WWW-Authenticate: Bearer` challenge, the cause recorded server-side only. | A transient outage fetching Google's signing keys is reported to callers as an authentication failure rather than as a server fault, which can prompt a needless re-authentication. Bounded: the exception class is logged on every occurrence, so the outage is visible in logs even though the status code does not distinguish it. |
| R6 | N-1 | Key each Firebase Admin app by the project it verifies against, instead of initialising one process-global default app. | Keep the single default app and document that a project change needs a restart; re-initialise on change; validate that the cached app's project still matches. | `firebase_project_id` is read on every request, so a value that only takes effect after a restart is a trap: the setting appears to apply and silently does not, and tokens keep being validated against the previous project. Naming the app after the project makes the cache key the thing that varies. | A process that sees several project values holds several initialised apps. Bounded by the number of distinct configured projects, which is one in every real deployment. |
| R7 | C-1 | Stop ignoring `.terraform.lock.hcl`, add a `terraform` block with `required_version` and a `required_providers` constraint, and commit the lock with hashes recorded for every platform the project builds on. | Keep ignoring the lock and pin only in `required_providers`; ignore the lock and pin nothing; commit the lock without a version constraint. | An ignored lock file means each `terraform init` may select a different provider version, so the plan that a reviewer approves is not necessarily the plan that applies — provider drift changes IAM, TLS and header behaviour silently. The constraint bounds the range and the committed lock fixes the exact build inside it; either alone leaves a gap. | The lock must be refreshed deliberately when the constraint moves, and a lock recorded for too few platforms fails a build on an unrecorded one. **Superseded by R28**: both the lock file and the `terraform` block were subsequently withdrawn, so provider drift is an accepted residual rather than a closed one. |
| R8 | M-6 | Model the runtime and signer principals as two separate service accounts: `roles/iam.serviceAccountTokenCreator` is bound **on the signer account** with the **runtime account** as member, and the runtime account is reachable from the workload through GKE Workload Identity. | Keep the signer self-binding; grant the role at project level; give the runtime a downloaded key; make the runtime and signer the same account. | The signing call presents the runtime identity's access token while naming the signer account, so the runtime must be the member and the signer must be the resource. A self-binding grants the signer permission to impersonate itself, which no caller can use — the documented deployment could not actually sign.
