# Security Decision Log

The single source of truth for **why** each security control in this repository is shaped the
way it is. Code carries only terse statements of the threat closed and the contract enforced;
every alternative considered, every trade-off accepted and every deviation from a literal
reading of the requirements is recorded here.

Cite an entry by its ID (`D3`, `DEV-2`, `R7`). Source files carry no citation of these
entries — see R27 — so this file is found by name, and each entry names the artifacts it
governs.

**On the measurements cited below.** Several entries justify a choice with something that was
observed rather than reasoned. Those divide into two kinds, and the difference matters to anyone
re-checking them:

- **Reproducible from this repository.** Anything about response headers, middleware order, CORS
  behaviour, throttling thresholds, token lifetime, the origin grammar, signed-URL construction,
  the published header values in `SECURITY.md` or the dependency-audit gate is asserted by
  `backend/tests/test_security.py`
  (`PYTHONPATH=. python -m pytest backend/tests/test_security.py -q`) or by the `pip-audit`
  command recorded in D29. Re-run it and the claim either holds or fails. As of R34 to R39 this
  also covers the database seam: mapper configuration, the identity query against real tables, the
  schema projection off a row object, the resolved row's detachment, the driver and dialect
  contract, and the admitted request reaching a handler through the production dependency are all
  asserted, in `TestOrmSeam`, `TestAuthenticatedIdentityResolution` and
  `TestDatabaseDriverContract`.
- **One-off observations against live services, not re-runnable here.** The connection-pool
  measurement in DEV-5, the `422` in R26 and the PostgreSQL adaptation results in R30 were each
  measured against a running PostgreSQL instance or a route replica. No committed artifact
  reproduces them, so they are recorded as observations with their conditions stated, and a reader
  who needs to confirm one must reproduce the condition. That gap is deliberate rather than
  overlooked: reproducing them in CI would need a live database and a route the frozen contracts do
  not permit changing. Two claims have moved out of this list: the mapper failure DEV-6 recorded is
  now reproduced in the positive direction — `TestOrmSeam::test_the_mappers_configure` shows
  configuration completing where it previously raised — and residual 15's detachment is asserted by
  `TestAuthenticatedIdentityResolution::test_the_resolved_user_is_readable_after_its_session_closed`,
  which checks the instance is detached and that its loaded columns still answer. The
  `DetachedInstanceError` on the `workbooks` relationship itself remains an observation.

## 1. Remediation decisions

| D1 | Bridge identity by verifying the Firebase ID token inside the existing `get_current_user`. | (a) Mount a `/token` route issuing the existing HS256 JWT; (b) run both paths in parallel. | Fewest files touched given the Firebase-first client flow: 4 files versus 8 or more. It would also depend on the `passlib` + `bcrypt` path proven broken in D15. | Every request now performs token verification, so a Firebase outage becomes an authentication outage. Mitigated by `auth_token_verifier`, which selects the legacy path per request with no restart. |
| D2 | Resolve relational identity through the verified `email` claim rather than adding a `firebase_uid` column. | Add `firebase_uid` with a migration; key on the UID with no relational lookup; keep a separate mapping table. | `User.id` is an `Integer` primary key with no `firebase_uid` and no password column, and the repository has **no migration tooling** — `scripts/deploy.sh` still carries an unresolved "specify the migration tool" placeholder. `User.email` is unique and non-null, so it is the only mapping needing no schema change. | Runs against Firebase's own guidance that email addresses change while UIDs never do. | D3 | Return a V4 signed URL from `upload_file` rather than proxying object bytes through an authenticated endpoint. | An authenticated backend proxy streaming object bytes; a short-lived per-object token scheme. | Signed URLs were the first-listed preference and the change is confined to two lines inside an existing method. | D5 | Enforce public access prevention on `user_uploads` but only uniform bucket-level access on `static_assets`. | Enforce on both; enforce on neither; serve the SPA from a private bucket behind Cloud CDN. | `static_assets` intentionally serves the public SPA, and enforcing public access prevention there would break the site. | D6 | Implement rate limiting as middleware — a global ceiling plus a write-method tier — rather than per-route decorators. | `@limiter.limit` decorators per endpoint; an API-gateway quota; Cloud Armor. | Decorators require a `request: Request` parameter on every handler, which the "no refactoring beyond the auth dependency" boundary forbids. Two details recorded here do not: the ceiling is no longer "global" only in name — R32 replaced the `slowapi` implementation because its `default_limits` were counted per endpoint function and unmatched paths were exempt entirely — and the store and client-identity configuration described in an earlier correction is gone. The risk noted above is also narrower now, because R41 raised the write budget and tied it to the client's coalescing window. |
| D7 | Use `sslmode=require` with Cloud SQL `ssl_mode = "ENCRYPTED_ONLY"`. | `sslmode=verify-full` with `TRUSTED_CLIENT_CERTIFICATE_REQUIRED`; the Cloud SQL Python Connector. | The mandate was a configuration-only change. `verify-full` needs CA material distributed to the client and connection by DNS name; the Connector needs a new dependency and new connection code. | `require` encrypts but does not authenticate the server, so it defeats passive interception but not a determined active machine-in-the-middle. | D8 | Set only `ssl_mode` in Terraform, never the legacy `require_ssl`. | Set both; set `require_ssl` alone. | `ssl_mode` is the current attribute and supersedes `require_ssl`; setting `ssl_mode` while the provider defaults `require_ssl` to false produces a conflict. | A provider version that still requires `require_ssl` would fail the plan. | D9 | Deliver security headers at four points: API middleware, `index.html` meta tags, `nginx.conf`, and Terraform backend-bucket custom response headers. | Nginx only; meta tag only; API middleware only. | The compiled SPA ships to a Cloud Storage bucket by `gsutil rsync` while the Nginx image is never deployed, so Nginx-only headers would reach nobody. CSP's `frame-ancestors` is ignored inside a `<meta>` tag, so the meta tag cannot deliver framing protection. Each point covers a path the others do not. | Four places to keep consistent; drift is possible. Mitigated by defining the canonical set once in `backend/app/core/security_headers.py`, referencing it from each artifact, and rendering the variable part rather than duplicating it (R10, R11). **Clarified by R35:** "four points" was a convenient shorthand that later read as a claim of four equal producers, which they are not. | D18 | Provide `auth_enforcement_enabled` as a break-glass switch, defaulting to `True`, with mandatory warning logging and a response marker when disabled. | Omit it entirely; make it staging-only. | The requirement was explicit: the auth dependency must ship behind a toggle that can be disabled quickly without a full redeploy. | **Corrected twice, and the second correction reverses the first.** The original entry said exercising the switch "reopens V1 in full." A later revision called that an overstatement and claimed a Bearer token remained mandatory because `OAuth2PasswordBearer` would refuse a missing credential first. **That claim was false, and the original was right.** `oauth2_scheme` is constructed with `auto_error=False` — deliberately, and R2 is where that choice was made — precisely so that the enforcement switch is read *before* a missing credential is refused. ### 3.1 Decisions taken while resolving the infrastructure-to-integration review

The review that prompted these found nineteen issues, five of them deployment blockers. The
pattern behind most of them is one thing: `infrastructure/terraform/main.tf`, `variables.tf`,

together — so a resource could be renamed while a script still instructed an operator to apply
it, a Terraform argument could be withdrawn while a script still asserted the value it produced,
and a variable could be documented as a security control while nothing read it. Several rows here
therefore record a **test** as part of the decision, because a decision that only two files agree
about is one edit away from being untrue again.
